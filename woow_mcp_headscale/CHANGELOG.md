# Headscale Add-on changelog

## 0.5.0 — multiple profiles

- Main reason for this release: multiple profiles are switched on for this add-on (train B, with Hermes and n8n; Odoo was first, then EMQX, LiteLLM and Nextcloud). Beside the default profile (the settings and token you have today), a Home Assistant administrator can add up to three more profiles in the admin panel (fewer when memory or open files are short: adding one then answers HTTP 409). Each profile has its own Headscale connection (URL and API key), its own MCP token with its own two connection URLs, its own tool policy and its own MCP child, and only the token of a request decides its profile. Profiles may use the same Headscale server with different tool policies, or different servers. Profiles are not tenants: every child runs as the same user, so one compromised child controls the whole add-on and every profile (see DOCS). Back up the add-on before updating: Home Assistant cannot install an older version over this one, and going back means restoring that backup.
- An installation that never adds a profile keeps its token, both connection URLs, its `state.json` byte for byte, its tool policy, its child on port 3000 with the same working directory, the 15-second health check interval and the key and format of the default profile's operation receipts. What it still sees change is listed below; the multi-profile groundwork that earlier images carried switched off (PRs #91, #93, #95, #99, #101–#104, #107, #108, #110–#112, #114, #116, #136 and #137, and the Headscale, Hermes and n8n work merged with this release) is switched on in this image.
- This release is built on the 2026-11-25 maintenance release (0.4.20), so it also carries everything that release changed (updating from 0.4.19 goes straight to this version): the admin panel accepts Home Assistant Core 2026.11.3 and any later patch release of a Core month this version has reviewed (2026.7 to 2026.11), and the panel build stage uses the Node 26.13.1 base image; this image has no Node.js of its own, so the runtime is unchanged by it. Its entry below has the details.
- The panel no longer shows the current MCP token, with only the default profile as well (aligned with the PaaS server; every other product still shows it): the "顯示權杖" (show token) button is gone and `token/reveal` answers HTTP 404 for Headscale; "顯示 Claude.ai 連線網址" became "產生新的 Claude.ai 連線網址", which rotates the token first. To get a token you rotate it ("重新產生"): the old token and both old URLs stop working at once, and the new token is shown once, briefly. A client that holds the current token keeps working until you do; a profile you add has to be rotated once to get its first token shown.
- Admin panel: a profile menu at the top, also with only the default profile, to add, rename, delete (two confirmations; the default profile cannot be renamed or deleted) and switch profiles; each profile has its own pages (overview, backend connection, tool permissions, connection and token, diagnostics and maintenance). The selected profile is kept in the page's memory only, so a reload returns to the default profile. A new profile copies the default profile's current tool policy (separate afterwards) and starts with no backend connection. The MCP client endpoint stays one setting of the whole add-on, set on the default profile. Every time the panel opens, its first bootstrap request deliberately carries no profile header, so the browser console shows one HTTP 400 (`profile_id_required`): expected.
- Admin API (port 8099): every profile-scoped request must carry exactly one `X-MCP-Profile` header (`default` or the profile's id): without it HTTP 400 `profile_id_required`, with more than one or a malformed value HTTP 400 `profile_id_invalid`, an unknown profile HTTP 404 `profile_not_found` (never the default profile instead). The bootstrap adds `profile`, `profiles_supported` and `profile_index_state`, and every other profile-scoped JSON answer adds `profile` (`{"id"}`). The bundled panel and the P9 acceptance kit of this version send the header; a script of your own that calls the admin API must add it. The HA administrator check now runs before any profile state is looked at, so every admin request, pages and static files included, makes one more HA Core role query. New global routes: the profile list, add, rename and delete, "revoke all", the restore record and its review, quarantining an unusable profile index and deleting a quarantine directory (Headscale has no Origin policy, so `/api/origin-policy` answers 404); the 202 answer of `child/restart` adds `blocked_reason`.
- Admin API (port 8099): a PATCH or DELETE request that fails the identity check (for example one without the CSRF header) now gets HTTP 403 `{"error":"request denied"}` from that check (HTTP 400 with the same body when its `X-Ingress-Path` header is malformed) instead of HTTP 405 `Method Not Allowed`, because the identity check now runs before the method check.
- Admin API (port 8099): a request with any method other than GET, HEAD, POST, PUT, PATCH and DELETE (for example OPTIONS) still gets HTTP 405 `Method Not Allowed`, but its `Allow` header now lists six methods instead of four (`PATCH` and `DELETE` are added). The order of the methods in that header has never been fixed.
- MCP (port 8081), admission per profile: when the default profile has more than 64 requests in progress, a further request now gets a JSON-RPC busy answer instead of uvicorn's plain-text 503: HTTP 200 with `-32003` and `Retry-After: 5` for a body of at most 64 KiB with an id, HTTP 503 otherwise; at most 32 requests wait for a forwarding slot, and one that gets none within 1 second is answered with `-32003`. Each additional profile has its own 32 (16 forwarding, 16 waiting). The GET stream quotas are 24 for the default profile and 8 for each additional profile: a further GET stream of the same profile gets HTTP 429 with `-32003` and `Retry-After: 30`. The listener's outer bound grows to 160 connections (64 + 32 for each of the three additional profiles); the default profile's own bound stays 64.
- MCP (port 8081), memory: replies processed but not yet taken by the client are capped at 32 MiB per profile (it holds back only `tools/call`, and replies already forwarded to the child are still delivered, so it is a soft cap). The request byte budget is now derived with the capacity of every enabled profile counted (the default profile plus up to three additional ones, each child counted at 160 MiB), so the per-profile share can be smaller than in 0.4.14. The 64 MiB reply tickets of Odoo 0.5.0 do not apply to this product: it keeps the ordinary 32/16 forwarding slots and the 24/8 stream quotas.
- MCP (port 8081): a token rotated or revoked while its answer is being sent now ends that answer with JSON-RPC `-32005`, and a child that disconnects in the middle of an answer with `-32004` (the operation may or may not have completed), and the add-on log no longer gets a traceback of about 40 lines for them. Replies are processed on one worker thread, profile by profile in turn (the bytes are unchanged, the latency is distributed differently).
- Secret URL Origin check: unchanged for Headscale, and not the list the other products get. Every profile's secret URL keeps the Headscale rule (no Origin, or exactly `https://claude.ai`; any other Origin is refused with HTTP 403), there is no `origin-policy.json`, no report-only mode and no "瀏覽器來源檢查" card. A Bearer `/mcp` request with an Origin header is refused with HTTP 403 as before, and no CORS header is added.
- Child and health (every profile): the watchdog follows the PaaS server, restarting a child after 2 to 300 seconds of backoff without a limit on attempts and resetting after 120 seconds of running; a failed spawn is retried the same way (before: at most 4 starts per add-on start, then `failed`). The backend counts as unreachable after two failed health checks in a row; when the Headscale server refuses a profile's API key (HTTP 401: revoked, expired or wrong), that profile's checks back off to 15, 30, 60, 120 and then 300 seconds apart (normally every 15 seconds) until new credentials are saved, the child is restarted in the panel or the server answers anything else; the reason shown is unchanged; while a child is not running, its monitor does not probe it (`backend/test` answers `unknown` without a reason). Before the child on port 3000 starts, the port is checked: when something else holds it, the child is `blocked` and retried by the watchdog. The add-on log gets lifecycle warnings that name a profile by the first 8 characters of its id only, one of them when the platform refuses an IPv6 test bind.
- Open files: at start the soft `RLIMIT_NOFILE` is raised to what three additional profiles need plus 25% (about 530, never above the hard limit). When it cannot be read or raised that far, only the default profile is served, one warning is logged, and adding a profile answers HTTP 409 `profile_limit_reached` with `limit` 0, writing nothing.
- Memory: adding a profile, saving its backend connection when its child has to start for the first time and restarting its child by hand read `MemAvailable`; with less than 256 MiB plus 160 MiB for the child, adding answers HTTP 409 `profile_memory_insufficient` and a saved connection leaves the child `blocked` (`memory_capacity`). The default profile is never refused for memory. Nothing is checked at boot.
- A Headscale API key administers the whole Headscale server, and Headscale has no narrower key: profiles on one Headscale server are kept apart only by their tool policies, whatever keys they use. A profile allowed to create API keys (`headscale_api_keys` create) can obtain a key that administers the whole server and that no tool policy, no "Revoke all" and no restore check reaches, and a profile allowed to expire or delete API keys can stop the other profiles' keys: deny these operations to every profile meant to be restricted (the connection page says so once profiles are on). An API key of its own per profile is still recommended (not enforced): one profile's key can then be revoked in Headscale without stopping the others.
- A profile added in the panel starts without the API key writes: it copies the default profile's tool policy as before, except that `headscale_api_keys` create, expire and delete are not copied (listing API keys is). Turn them on in the new profile's tool permissions if it needs them. The default profile and profiles that already exist are not changed.
- Each profile's MCP child reads only its own profile's saved policy, at every call (also for calls made straight to the child inside the container); a profile directory whose owner or mode cannot be verified makes every call of that profile fail with `HEADSCALE_POLICY_UNAVAILABLE`.
- Hardening of the Headscale MCP child (HM-26 security review S-1; every installation, whatever the profile switch): at every call the child now also checks that the saved state it reads is its own, by comparing the state's child token with the `WOOW_MCP_CHILD_TOKEN` the add-on started it with (also for calls made straight to the child inside the container). A state of another profile, or one whose child token was replaced while the child kept running, makes every call fail with `HEADSCALE_POLICY_UNAVAILABLE` before anything is sent to the Headscale server. Nothing changes for a child the add-on started on its own state.
- Backend connection: moving a profile's Headscale URL to another server (a new scheme, host or port) now requires entering its API key again in the same save, otherwise HTTP 422 `CREDENTIAL_REPLACEMENT_REQUIRED_FOR_NEW_ORIGIN` and nothing is saved, so a saved key is never sent to a new server. The same origin written otherwise (the `/api/v1` root, letter case, the default port) needs no key.
- Backend connection: a loopback Headscale URL (127.0.0.0/8, ::1, `localhost`) is refused when it is saved (HTTP 400); the MCP child refused to connect to one before, and still does.
- Backend connection: changing a profile's Headscale URL or API key keeps its MCP token and both URLs, as before; only that profile's MCP child restarts with the new values.
- Saving a profile's tool policy restarts only that profile's MCP child; the other profiles' sessions and tool lists are not affected.
- A request whose JSON-RPC id is already in flight in the same MCP session (same `Mcp-Session-Id`; `7` and `"7"` are one id) is now refused at once with HTTP 400, JSON-RPC error `-32600` and `"id": null`, naming the id (PaaS #161), and is not sent to the MCP server; this holds for every connection of the add-on, whatever the profile switch. Before, the MCP SDK keyed both requests' answers by that id, so they overwrote each other: with eight such requests none got its own answer and seven hung until the gateway's own limit. The id can be used again once its request ended (answered, client gone, error, timeout or token change); notifications, `initialize`, GET streams, DELETE and the answers the gateway gives itself are not checked. Clients that use a new id for every request, as MCP requires, see no change: the official SDK clients do, and the Claude.ai and ChatGPT clients do not reuse an id either, so they do not trigger the refusal. At most 512 ids are tracked for the add-on and 32 per profile (16 per additional profile); beyond that, or for an id longer than 256 characters, the request is forwarded unchecked and one warning a minute is logged. The check sits in the gateway, in front of the MCP server.
- Behind a proxy that compresses the panel's answers (Cloudflare does), the add-on's strong ETag of the profile list (`"p1-…"`) can arrive as a weak one (`W/"…"`), which the panel did not take as a revision, so the profile list stayed read-only. The panel now reads the same revision from the weak form; it still sends the strong `If-Match` as before, and the add-on's comparison is unchanged. Measured on a real Home Assistant behind Cloudflare (2026-11-25), the profile list's ETag (`"p1-…"`) stays strong there, because Home Assistant compresses that answer itself; it can only turn weak when a proxy rewrites an answer that Home Assistant sent uncompressed, for example when the client does not accept compression.
- Files: the first start of this version adds two small files without secrets to `/data/mcp`, `.instance-sentinel` and `.instance-record` (the second restore signal). `profiles.json`, the `profiles/` directory and the index's operation receipts `.profiles.json.operations.json` appear only once a profile is added.
- Restore guard (PR #108): after Home Assistant restores this add-on's backup, the next start handles the restore before any listener or MCP child starts. It reads the restore marker `.restore-detected` that the entrypoint leaves (0.4.14 left it and kept it, also in later backups; this version removes it) and compares the instance sentinel, so a restore is detected by either signal. When the restored data has no additional profiles, nothing is revoked, as before: the log gets one warning that the MCP token is back to its value at the time of that backup (`restore guard: the data was restored from a backup; the MCP token is back to its value …`; rotate it in the panel if it may have leaked since), the panel's restore notice is saved (next point), `restore-record.json` is written with the default profile kept and nothing to review, and the operation receipts beside the profile index and the Origin policy are renewed, so a profile or Origin policy operation id from before the restore answers HTTP 410 `operation_restored` (the default profile's own receipts stay as restored). When the restored data has additional profiles, the token of every profile, the default profile's included, is revoked, every child token and the operation receipts renewed (an operation id from before the restore answers HTTP 410 `operation_restored`; one warning for the whole restore and one per profile); unreadable profiles are moved to a quarantine directory; the default profile's page then shows a review card, and a profile gets a new token only after it has been checked there (`token/rotate` answers HTTP 409 `restore_review_required` before). When a step cannot be finished (a full disk, say), that start serves nothing and starts no child, logs `restore guard: not finished (…)` and keeps every marker, and the next start does it again. A start without a restore only checks a few names and writes nothing. This protects backups made with this version or later; after restoring an older backup, update to this version and press "全部撤銷" (revoke all).
- After a backup restore that keeps the MCP token (no additional profiles in the restored data: nothing is revoked), the admin panel shows "偵測到還原；權杖已回到備份當時的值。若備份後曾輪替或撤銷，請立即重新產生" until the default profile's token is rotated or revoked (PR #112). Meanwhile the bootstrap carries one more field, `restore_notice` (`{"at"}`), and `/data/mcp` holds `restore-notice.json` (its time only, no secret). An installation that was never restored answers byte for byte as before.
- Going back: restore the add-on backup taken before this update (profiles added since are lost and the default token is the backup's; after updating again, press "全部撤銷" and issue new tokens). Switching profiles off again would be a release with a higher version (at least about a working day); meanwhile stop the add-on, or revoke a profile, delete it or press "全部撤銷" in the panel. See the repository's `docs/operations/update-backup-rollback.md`.
- The image is built and accepted by the GitHub-hosted release route; the published digest and the HAOS acceptance result are in ../../docs/operations/release-decision-headscale-0.5.0.md (written after the image is published).

## 0.4.20 — maintenance release

- Main reason for this release: the admin panel accepts Home Assistant Core 2026.11.3, and from now on also any later patch release of a Core month this release has reviewed (2026.7 to 2026.11), so a Core patch update no longer locks the panel until the next add-on release. The administrator check of 0.4.19 accepts Core only up to 2026.11.2, so on Core 2026.11.3, the version Home Assistant's stable channel offered on 2026-11-25, it refuses every admin panel request (the panel says the Core version has not been reviewed, and the add-on log gets one line); MCP endpoints do not use this check and are not affected. In 2026.11.3 the 25 Core contract and adjacent files are byte-identical to 2026.11.2 (the comparison of 43 commits and 76 files changes one file under a contract path, `components/auth/indieauth.py`, a header-size limit of the login flow's client page fetch, which is not on the `config/auth/list` path), and Supervisor 2026.11.0 ships the reviewed WebSocket proxy unchanged. The rule for later patch releases (owner decision 2026-11-25): the Core version must be exactly `year.month.patch` in ASCII digits without zero padding, its year and month must already have a reviewed release here, and its patch must be higher than every reviewed patch of that month (2026.11.4 and later after 2026.11.3; not 2026.7.0 or 2026.7.1, which are older than the first reviewed 2026.7.2). The first release of a new month (2026.12.0), pre-releases and any other form of the string stay refused until a release reviews them. Nothing else about the check changes: the machine token is sent only after the version check, `auth_required` and `auth_ok` must carry the same version, and the user's role is read afresh on every request. A version accepted by the rule without a review of its own gets one add-on log line per version and process, and the refusal's log line and panel text now say that a later patch release of a reviewed month is accepted.
- Restore guard (groundwork for multiple profiles; PR #108): after Home Assistant restores this add-on's backup, the next start now reads the restore marker `.restore-detected` (the previous release left it and kept it, also in later backups; this version removes it) before any listener or MCP child starts, logs one warning that the MCP token is back to its value at the time of that backup (`restore guard: the data was restored from a backup; the MCP token is back to its value …`; nothing is revoked without multi-profile data; rotate the token in the panel if it may have leaked since), saves the panel's restore notice (next point) and removes the marker. Apart from that notice file, nothing else in `/data/mcp` changes. If the notice cannot be saved or the marker cannot be removed, the add-on still starts, logs one more line and tries again at the next start. A start without a restore only checks a few file names and writes nothing.
- After a backup restore that keeps the MCP token (no multi-profile data on disk: nothing is revoked, as before), the admin panel now shows "偵測到還原；權杖已回到備份當時的值。若備份後曾輪替或撤銷，請立即重新產生" until the token is rotated or revoked (PR #112). Meanwhile the bootstrap carries one more field, `restore_notice` (`{"at"}`), and `/data/mcp` holds `restore-notice.json` (its time only, no secret). An installation that was never restored answers byte for byte as before; no management route is added.
- This image also carries more groundwork for multiple profiles per add-on (PRs #108, #112 and #116, and the multiple-profile work of Odoo, EMQX, LiteLLM and Nextcloud merged in #136 and #137). It stays switched off for this add-on: requests, responses, the admin panel and the files in `/data/mcp` are unchanged apart from the changes listed above.
- The panel build stage uses the Node 26.13.1 base image (was 26.12.1). This image has no Node.js of its own, and the built panel files are byte for byte the same as a build with 26.12.1 (checked locally with the official binaries of both versions), so the runtime image is unchanged by this.
- Advance only Headscale's own version line, from 0.4.19 to 0.4.20; the shared default version moves to 0.4.15.
- The image is built and accepted by the GitHub-hosted release route (PR #121); the published digest and the HAOS acceptance result are in ../../docs/operations/release-decision-headscale-0.4.20.md.

## 0.4.19 — maintenance release (image published and verified)

- Main reason for this release: the admin panel accepts Home Assistant Core 2026.11.2 (PR #120). The administrator check of 0.4.18 accepts Core only up to 2026.11.1, so on Core 2026.11.2 it refuses every admin panel request (the panel says the Core version has not been reviewed, and the add-on log gets one line); MCP endpoints do not use this check and are not affected. In 2026.11.2 the 25 Core contract and adjacent files are byte-identical to 2026.11.1, and Supervisor 2026.11.0 ships the reviewed WebSocket proxy unchanged. Later patches (such as 2026.11.3) and pre-releases stay refused until reviewed.
- Log redaction now applies the PaaS server's rules first and then the add-on's own (PR #98). In the add-on log, credential values in URL query strings show as `***`, and a record whose format string does not match its arguments shows `[redacted: invalid log message]`. In the log and in child output on the diagnostics page, a line whose URL encoding cannot be judged, or where the combined rules would show a part the old rules hid, is replaced as a whole with `[redacted: ambiguous URL encoding]`, and strings over 128 KiB are cut short. Child output also masks `key=` values, so ordinary text such as `cache key: x` is masked too, and a child line whose masking fails shows `line withheld (redaction failed)`. The `[REDACTED]` and `/private_[REDACTED]` forms are unchanged.
- The MCP child on the container's loopback port 3000 now serves only the gateway's own child bearer (PR #94): a direct request inside the container without exactly one `Authorization: Bearer <child token>` header gets HTTP 401 with no body, and the child refuses to start without a valid child token. Requests through port 8081 and the admin panel are unchanged.
- Restore detection (groundwork for multiple profiles; PR #97): after Home Assistant restores this add-on's backup, the first start leaves an empty, owner-only marker file `.restore-detected` in `/data/mcp`, and the restore repair log line counts it (`re-owned N restored entries`). A later version reads and removes it; until then it stays, also in later backups. If the marker cannot be saved, that start logs one line with the reason (an errno name such as `ENOSPC`, or `name in use`); with multi-profile data on disk (none today) the start is refused and retried at the next start. Starts without a restore are unchanged.
- If the MCP child answers `initialize` with an error that contains this add-on's own credentials (the MCP token, the child token, a backend secret or its Basic form), those parts now reach the client as `[REDACTED]`, as every other text the gateway passes on from the child or the backend already did (PR #103). The status code, the other headers and the rest of the text are unchanged (only `Content-Length` follows the new length); an error without credentials is returned exactly as before.
- Gateway request limits aligned with the PaaS server (PR #105): a request body over 64 KiB is read under a byte budget derived at startup from the container's memory limit, or from MemAvailable less 256 MiB when there is none (at least 16 MiB, at most 64 MiB for the add-on's profile). What counts is the larger of the body as received and as forwarded to the add-on's MCP server, which escapes non-ASCII text, so Chinese text counts about twice its size and emoji about three times (with the smallest 16 MiB share, a 6 MiB body of emoji is refused); a Content-Length sent together with Transfer-Encoding is ignored and the bytes that arrive are counted. A large body the budget cannot hold is answered with JSON-RPC error -32003 and `Retry-After: 5` (HTTP 200 under its id when its head or tail shows it, else 503) instead of being processed, and one that sends nothing for 30 seconds is dropped with HTTP 408 (`-32003`, `Connection: close`); the 60-second whole-read limit and its 408 are unchanged. A body that declares more than 16 MiB gets the same HTTP 413 as before, now before any of it is read. A JSON body nested deeper than 64 levels or with more than 200,000 elements is refused before it is parsed (HTTP 200 with `-32602` under its id when its head or tail shows it, else 413); so is a body that is not UTF-8 (UTF-16 and UTF-32 bodies were processed before; invalid UTF-8, and malformed JSON with that much structure, got HTTP 400 before). Requests within these limits are answered exactly as before; each kind of refusal writes one warning a minute.
- Fixed: stopping the add-on could wait for Home Assistant's 30 s stop timeout in rare cases (PR #106).
- dnspython in the MCP child's environment goes from 2.9.0 to 2.9.2 (GHSA-vvf4-9x63-8xvv, CVE-2026-128089, High): 2.9.0's zone-file parser sizes a WKS record's bitmap from an unchecked service number, so crafted zone text can exhaust memory or CPU. Here dnspython is only email-validator's dependency and no zone file is parsed; the update clears the release scanner's block on this fixable High vulnerability. The 0.4.18 image carries 2.9.0.
- This image also carries the groundwork for multiple profiles per add-on (PRs #91, #93, #95, #99, #101–#104, #107, #110, #111 and #114). It stays switched off for this add-on: requests, responses, the admin panel and the files in `/data/mcp` are unchanged apart from the changes listed above.
- Image published and verified on 2026-11-18: `ghcr.io/woowtech/amd64-mcp-headscale:0.4.19` (manifest `sha256:a05e1a35fe3a048590b34fb542a38bd9a2fa2883d5151bd5732903d7c44baed9`), the exact image the GitHub-hosted release route tested (PR #121). HAOS acceptance, the Stable Release and Store distribution remain separate gates.

## 0.4.13 — first stable release
