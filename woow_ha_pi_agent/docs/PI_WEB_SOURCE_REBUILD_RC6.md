# RC6 Pi Web source rebuild provenance

RC6 builds the official Pi Web 0.12.0 source at `agegr/pi-web` tag `v0.12.0`, resolved to commit `894e1a28dbeeb7b457c7712e495d975fe9927b89`. The release npm package is not used as the build input because it contains the old Next 16.3.8 compiled tree. Docker fetches the tag, verifies the commit, applies `patches/pi-web-source/pi-web-0.12.0-next-16.4.6.patch`, verifies the patch and resulting package/lock hashes, runs `npm ci`, `npm audit --audit-level=high`, and builds the source before production pruning.

The reviewed patch keeps Pi Web at 0.12.0, pins `next` and `eslint-config-next` to 16.4.6, and updates the lock including the undici 8.12.2 security fix. It changes session JSON handlers to return plain JSON so the Next production server owns content compression; manually gzipping inside the handler caused double/invalid compression with Next 16.4.6. Build ID is fixed for identical source and lock inputs. The existing HA CJK path, ChatGPT device-id and Omnigent/Agent Connect settings patches run against the rebuilt output and remain hash/anchor gated. The CJK patch runs before and after compilation; its marker makes the second application byte-idempotent. Before the final runtime COPY, the builder removes and asserts absence of the source `.git`, `.next/cache` and `node_modules/.cache`; the local source build measured `.git` at 9.6 MiB and `.next/cache` at 666 MiB, so these must not enter the runtime layer.

`patches/pi-web-source/build-pins.json` is the machine-readable source, lock, patch and version record. Local validation built the source tree only (no container image) and ran the sessions route tests, the compiled settings patch suite, and a live loopback HTTP acceptance against this source build. The live test covered 24 owned synthetic sessions, raw single-layer gzip, and ordinary `fetch().json()` parsing. CI still needs to build the supported amd64 and aarch64 images and run the upgrade comparison; this candidate has not passed those release gates.

## Build root and re-deriving the compiled pins

Next.js module IDs embed the absolute app directory, so the compiled client chunk, the SSR page, the flight reference files and even the chunk file name change with the build root; `npm ci` and `npm install` can also produce different minified identifiers. `patches/patch-omnigent-settings.mjs` therefore pins the output of one exact environment: the tree built with `npm ci --include=dev` at `/opt/piweb-source/package`, the fixed root used by both CI and the Dockerfile (the runtime path `/opt/piweb/lib/node_modules/@agegr/pi-web` is a symlink to it). A project root nested inside `node_modules` is not a valid source-build root for Next 16.4.6.

After any Pi Web, lockfile or build-root change, run `node patches/print-compiled-settings-pins.mjs /opt/piweb-source/package` on a fresh build. It never writes and reports the actual client/SSR hashes, the chunk file name, every reference hash and how many times each source anchor occurs. CI runs it before the strict settings test, so one failing run shows every value to update. The strict patch and its tests remain the fail-closed gate.
